# Banking Transaction Data Pipeline & Risk Analytics

End-to-end, fully local data-engineering portfolio project: generate a
realistic synthetic banking transaction dataset, explore and clean it,
process it with PySpark, store it in MySQL, and perform SQL-based banking
and rule-based risk analytics - all reproducible on a normal laptop, no
cloud services required.

> **Disclaimer:** This project uses 100% synthetic data. The risk analytics
> are explainable rule-based *indicators*, not real fraud detection.

---

## Overview

Banks process millions of transactions daily. Raw extracts almost always
arrive with data-quality problems - missing values, duplicates, inconsistent
formats - and analysts need clean, well-modeled data to answer business and
risk questions. This project simulates that reality end-to-end:

```
Generate raw data (with realistic defects)
        |
        v
EDA (Pandas + Matplotlib/Seaborn)
        |
        v
Data quality checks  ->  Data cleaning (Pandas)
        |                                    |
        v                                    v
Data-quality report              Cleaned CSV
        |                                    |
        +----------> PySpark ETL <-----------+
                          |
              +-----------+-----------+
              |                       |
        Aggregated CSVs         MySQL (via JDBC)
              |                       |
              v                       v
        Risk scoring          SQL analytics
        (Pandas + SQL)        (25+ queries)
              |                       |
              +-----------+-----------+
                          v
              Final insights report
```

## Business Problem

- How do we turn a messy raw transaction extract into a trusted,
  analytics-ready dataset?
- What do transaction volumes, values, channels and failure rates look like?
- Which customers are most valuable / most active?
- Which transactions show *unusual* patterns that a human analyst should
  review (e.g., amounts far above the customer's normal behaviour,
  rapid-fire transactions, unusual international activity)?

## Objectives

1. Generate 50,000+ realistic synthetic transactions covering ~1 year.
2. Deliberately inject realistic data-quality issues.
3. Measure those issues with an automated data-quality report.
4. Clean, validate and enrich the data.
5. Run the same pipeline through PySpark to demonstrate distributed ETL.
6. Model the data relationally in MySQL and load it via JDBC.
7. Answer 25+ business questions in SQL (CTEs, window functions, joins).
8. Score transactions with explainable risk rules (LOW/MEDIUM/HIGH).
9. Auto-generate a final insights report - every number comes from the data.

## Dataset

`data/raw/banking_transactions_raw.csv` - ~55,000 rows x 25 columns
generated by `python/generate_data.py` (seed = 42, fully reproducible).

Fields: transaction_id, customer_id, account_id, transaction_date/time,
transaction_type, amount, balance_before/after, account_type,
customer_age, customer_gender, city, state, branch, channel,
merchant_category, payment_method, transaction_status, device_type,
is_international, country, failed_attempts,
previous_transaction_amount, customer_risk_score.

**Realistic relationships:** ATM txns use the ATM channel/device; POS txns
are card payments; mobile/internet banking uses UPI/IMPS/NEFT/RTGS;
international txns have a foreign country; failed txns usually have
`failed_attempts > 0`; amounts vary by transaction type; customer/account
IDs repeat naturally across transactions. A small set of customers also
perform "rapid-fire" bursts (5-8 same-day transactions) to exercise the
daily-activity risk rule.

**Intentionally injected data-quality issues** (documented in
`outputs/reports/data_quality_report.csv`):

| Issue | Scale |
|---|---|
| Missing values (city, customer_age, merchant_category, payment_method, balance_after) | ~1-2% |
| Duplicate full rows | ~275 |
| Duplicate transaction_ids | ~440 |
| Invalid amounts (<= 0) | ~275 |
| Invalid/garbled transaction dates | ~110 |
| Impossible customer ages (4, 150, -5, 200) | ~55 |
| Inconsistent capitalization ("UPI"/"upi"/"Upi", "Male"/"male"/"M") | ~10-20% of category values |

## Data Cleaning

`python/data_cleaning.py` performs, in order:

1. Drop fully duplicated rows; drop duplicate transaction_ids (keep first).
2. Standardize column names and categorical values (case/whitespace).
3. Handle missing values ("Unknown" for categoricals; median for age;
   recalculated `balance_after`).
4. Parse/validate dates & numerics; drop unparsable dates and
   non-positive amounts.
5. Clip customer age to a realistic [15, 100] range.
6. Recalculate `balance_after` where missing.
7. Add derived fields: `transaction_year/month/day/hour`,
   `transaction_amount_bucket`, `customer_age_group`.

Output: `data/processed/banking_transactions_cleaned.csv` (~54,600 rows).

## PySpark ETL

`pyspark/banking_etl.py` implements:
`RAW CSV -> explicit schema ingestion -> validation -> cleaning ->
transformation -> aggregation -> output`.

**Why PySpark for a 55k-row dataset?** Pandas alone would technically
suffice - but PySpark is used deliberately to demonstrate the skill set
of a Data Engineer: explicit schema enforcement (vs `inferSchema`),
lazy declarative transformations (`select`/`filter`/`withColumn`/`when`/
`groupBy`/`agg`/`join`/`orderBy`/`dropDuplicates`), and the
ingest-validate-clean-transform-aggregate-load pattern real banking
pipelines use at billions of rows. Same code, any scale.

Outputs (CSV, under `data/processed/spark_output/`):
`cleaned_transactions`, `customer_summary`, `monthly_summary`,
`branch_summary`, `payment_method_summary`, `risk_transaction_summary`.

Requires a JDK (Java 11/17) plus `pyspark`. Run:

```bash
python pyspark/banking_etl.py
```

## MySQL Database

```bash
mysql -u <user> -p < sql/create_database.sql
mysql -u <user> -p banking_analytics < sql/create_tables.sql
```

To load cleaned data + aggregates into MySQL from the ETL script, set
environment variables (credentials are never hardcoded) and place the
MySQL Connector/J jar on the Spark classpath:

```bash
export MYSQL_HOST=localhost
export MYSQL_PORT=3306
export MYSQL_DB=banking_analytics
export MYSQL_USER=<user>
export MYSQL_PASSWORD=<password>
export MYSQL_JAR_PATH=/path/to/mysql-connector-j.jar
PYSPARK_DRIVER_CLASSPATH=$MYSQL_JAR_PATH python pyspark/banking_etl.py
```

## Data Model

```
customers ───┐                              ┌─> transaction_risk
             │ 1:N                          │
             v  1:N                         │
          accounts ───────────────> transactions ─> monthly_transaction_summary
```

- `customers` (PK `customer_id`): customer master with risk score + age group.
- `accounts` (PK `account_id`, FK `customer_id`): account type, city/state/branch.
- `transactions` (PK `transaction_id`, FK `account_id`): fact-style table holding
  every transaction plus pre-computed derived fields. Indexed on
  `customer_id`, `account_id`, `transaction_date`, `transaction_type`,
  `transaction_status`, `(year, month)`.
- `transaction_risk` (PK `transaction_id`): per-rule flags, `risk_score`,
  `risk_level` produced by `sql/risk_analysis.sql`.
- `monthly_transaction_summary`: pre-aggregated monthly rollup.

In warehouse terms: `transactions` is the **fact table**;
`customers`, `accounts` (and the implicit date dimensions via
`transaction_year/month/day`) act as **dimension tables** - a simple,
intentionally un-overcomplicated star-like model.

## SQL Analysis

`sql/analytical_queries.sql` - 25 annotated queries covering volume/value,
success rates, monthly trends, top customers/branches/cities, channel and
payment-method usage, account-type comparison, outlier customers, and
month-over-month growth. Techniques: JOIN, GROUP BY, HAVING, CASE, CTEs,
subqueries, window functions (`RANK`, `ROW_NUMBER`, `LAG`, `SUM OVER`,
`AVG OVER`).

## Risk Analysis

`sql/risk_analysis.sql` (SQL) and `python/risk_analysis.py` (local pandas
equivalent) implement six explainable rules - e.g., amount > 5x the
customer's own average (+40), unusual international +30, >=5 same-day
transactions +15, multiple failures +20. Rule hits are summed into a
`risk_score` and bucketed:

- `score == 0` -> LOW
- `10 <= score < 40` -> MEDIUM
- `score >= 40` -> HIGH

A customer-level `customer_risk_profile` aggregates totals, failures,
international and high-risk counts per customer. All outputs are
*review indicators*, not fraud verdicts.

## Key Insights

Computed from this project's synthetic dataset
(see `outputs/insights/final_insights_report.md` for the full auto-generated
report - re-run `python python/generate_insights.py` after regenerating
data to refresh):

- **54,614** clean transactions totaling **INR 294.3M**;
  average transaction **INR 5,388**; success rate **90.26%**.
- **4,000** customers / **5,176** accounts; ~13.7 transactions per customer.
- **Mobile Banking** is the most-used channel (16.8k txns); **ATM** has the
  highest failure rate (~7.1%).
- **Cash** is the most-used payment method; **UPI** carries the largest
  non-cash value (INR 54.9M).
- **962 HIGH-risk transactions (1.76%)** across 887 customers; the most
  common indicator is amount > 2x the customer's previous transaction.

## How to Run (end-to-end)

```bash
# 0. Setup
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

# 1. Generate raw synthetic data (with intentional defects)
python python/generate_data.py

# 2. Produce the data-quality report
python python/data_quality.py

# 3. Clean & enrich -> data/processed/banking_transactions_cleaned.csv
python python/data_cleaning.py

# 4. Run the EDA notebook (optional - it's already executed with outputs)
jupyter nbconvert --to notebook --execute --inplace \
    notebooks/01_EDA_Banking_Transactions.ipynb

# 5. PySpark ETL (needs Java - set JAVA_HOME)
python pyspark/banking_etl.py

# 6. MySQL (optional - needs a local MySQL server + connector JAR)
mysql -u <user> -p < sql/create_database.sql
mysql -u <user> -p banking_analytics < sql/create_tables.sql
# then run the JDBC load via banking_etl.py with MYSQL_* env vars set

# 7. Risk scoring (local, pandas) -> risk_transactions.csv
python python/risk_analysis.py
#    (or, in MySQL: mysql -u <user> -p banking_analytics < sql/risk_analysis.sql)

# 8. Final auto-generated insights report
python python/generate_insights.py
```
